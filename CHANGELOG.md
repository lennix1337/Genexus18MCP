### Added

- **Model-evaluation scoreboard and manual workflow.** `scripts/run-agent-model-eval.py` gains `--profile` (the `tools/list` served under each tool profile, from per-profile fixtures written and verified by `ToolProfileListFixtureTests`), `--strict` (scores without the always-acceptable `genexus_whoami`; lenient and strict numbers are both reported) and `--markdown` (adds or replaces the row for a model and profile in `docs/agent-eval-scoreboard.md`, which stays empty until a real run is recorded). The seven corpus scenarios without a first-tool expectation are now listed with their reasons. `.github/workflows/agent-evals.yml` runs the harness on `workflow_dispatch` only, with the `ANTHROPIC_API_KEY` repository secret, and publishes the report as an artifact and job summary; it never runs on pull requests or pushes and commits nothing. No model run has been executed yet.
- **`gx_legacy_kb_assessment` prompt.** A text-only MCP prompt that guides an agent through a read-only migration assessment of a legacy KB (GeneXus 8/9, 15, Evolution 1-2): inventory by object type, what the legacy driver cannot read (`UNSUPPORTED_IN_GENEXUS_VERSION`), and what needs manual review. It uses only published read tools, adds no tool and nothing to `tools/list`. Not yet tried against a real legacy KB.
- **`adaptive` tool profile.** Opt-in (`Server.ToolProfile` / `GXMCP_PROFILE` = `adaptive`, not combinable). `tools/list` returns the 15 `core` tools plus `genexus_tools` (361 characters), about 6.8k tokens against about 25.7k for `all` and about 11.0k for `standard` (characters / 4). `genexus_tools action=list` shows six groups and `action=enable group=<name>` adds one to that session's `tools/list` and sends `notifications/tools/list_changed` to that session only. A `tools/call` for a published tool that is not listed still runs and enables its group, so no tool is ever refused. The selection is per session (stdio process or `MCP-Session-Id`, dropped on `initialize` and on session end); the sessionless 2026 transport keeps none. Clients that ignore `list_changed` must call `tools/list` again; the enable result says so. Adaptive `tools/list` responses are `no-store`/`private`. Default and existing profiles are unchanged, `tool_definitions.json` is untouched, and the meta tool is added in code only for this profile.
- **Opt-in git history of KB changes.** With `GXMCP_KB_HISTORY=1` the Gateway commits every confirmed single-part `genexus_edit` write and `genexus_delete_object` deletion to a per-KB shadow repository outside the KB folder (`%LOCALAPPDATA%\GxMcp\history`, or `GXMCP_KB_HISTORY_DIR`), so `git log`, `git diff` and `git blame` work per object. The part text comes from the Worker's persisted-read receipt (no extra read), commits run on a bounded background queue after the response is sent, and a missing git disables the feature with one log line. Off by default, no new tool. See `docs/kb-history.md`.
- **Opt-in model evaluation harness.** `scripts/run-agent-model-eval.py` measures a model's first-call tool selection against the served `tools/list` and `initialize` instructions, with expectations for 8 scenarios in `tests/agent-evals/first-tool-expectations.json`. It is tested offline only and has not been run against a live model.
- **`logging` capability.** `initialize` and server discovery now declare `logging`, and `logging/setLevel` gates `notifications/message`. Behaviour is unchanged until a client sets a level.
- **`genexus_create` creates a Master Page (`type=MasterPage`).** The type answered `UnsupportedObjectType`. A Master Page is a WebPanel with `WEB_COMP=Master` whose form holds a `ContentHolder`, and the SDK refuses `WEB_COMP=Master` on a WebPanel whose form has no place holder, so building one through the MCP took two calls in a fixed order and left a WebPanel that the SDK does not accept in between. The Master Page is now created whole: `WEB_COMP=Master` and a form holding a `ContentHolder` go into the object together before its single save, and a fresh read confirms the result (an object proved not to be a Master Page is deleted again and answers `MasterPageNotPersisted`; one that cannot be read back is kept, with its persistence unverified). `folder`/`module` place it as for any other type, `dryRun` shows the plan, and `Master Page` and `Web Master Panel` are accepted spellings. `object_atomic` still does not create a Master Page (`UnsupportedObjectType`, also for a dry run) but updates an existing one, and `action=save_as` of a Master Page, which stopped at its first step (`PartialFailure`), now clones it with its form and parts.

### Changed

- **Self-update requires a checksum.** A release without a readable `publish.zip.sha256`, or with a mismatching one, is refused instead of being staged after structural validation only. `SECURITY.md` documents the mechanism and no longer carries a stale per-version support table.
- **Release builds require the engine binaries.** `build.ps1 -RequireEngineBinaries` (used by `release.ps1`) fails when `gx-engine.exe` or `gxwire.exe` is not produced, and the release manifest, `verify-release-manifest.py` and `verify-install.js` require both for versions above 4.6.0. Older releases still verify.
- **gxwire release builds use `opt-level = 3`.** Search and pack queries are about 1.5-2x faster on a 50k-node benchmark; the binary grows from 1.2 MB to 1.7 MB.
- **The npm package no longer ships CLI tests.** `cli/**/*.test.js` and `cli/test-support` are excluded, and CI runs `scripts/check-pack.js` to keep them out.
- **Tool results no longer carry a duplicate `structuredContent` by default.** `Server.EmitStructuredContent` now defaults to `false` (configs written by `genexus-mcp init` already set it), cutting every tool response by 28-49% in bytes (about 46% for typical query/read/build payloads). Tools that declare an `outputSchema` (`genexus_lifecycle`) still carry it, as the MCP spec requires. Opt back in with `Server.EmitStructuredContent: true` or `GXMCP_EMIT_STRUCTURED_CONTENT=1` (the latter was ignored on the response path and now works; `GXMCP_NO_STRUCTURED_CONTENT=1` still wins). Clients that read only `structuredContent` must set the option or read `content[0].text`; the gx-engine evidence validators now read either.
- **Release builds of the Gateway, its tests and the benchmarks treat warnings as errors.**

### Fixed

- **Multi-target `genexus_edit` can no longer blank a part while rolling back.** A target whose current part cannot be read is not written (`RollbackSnapshotUnavailable`), a write that throws is caught and rolled back instead of leaving earlier targets written, and rollback never restores an unknown original as empty. The failed target is checked by readback and reported in `rollback.failedTarget` with `failedAt`, `failureCode` and `reconciliationRequired`.
- **Source search no longer certifies stale text as fresh.** Only text read from the SDK in that scan is written to the durable source store, and the KB watcher clears an externally changed or deleted object's read-cache entries before updating its index entry.
- **`genexus_wire` argument injection.** Arguments reach gxwire as a real argument list instead of one interpolated command line, and caller-supplied values that start with `-` are rejected, so a crafted target can no longer add flags such as `--cache-path`.
- **Tool annotations follow `OperationClassifier`.** Tools that can overwrite or delete existing state (including `genexus_io`, `genexus_db`, `genexus_lifecycle` and 15 others) now carry `destructiveHint=true`; mutating-but-additive tools stay non-destructive, and a contract test fails when annotations and the classifier drift apart.
- **HTTP port recovery no longer kills unrelated processes.** It matches the listening port exactly (`:5000` no longer matches `:50001`), reclaims the port only from a `GxMcp.Gateway` process, runs only when the bind failed because the address is in use, and logs the configured port.
- **Agent hints no longer lead to dead ends.** `InvalidArgs` points to `genexus_whoami`, removed-tool replacements point to published `genexus_db` actions, the oversize-response follow-up carries each tool's real pagination arguments, and `genexus_wire`, `genexus_read` and `genexus_query` no longer tell agents to call `genexus_wire` first on a native KB.
- **Legacy HTTP proxy no longer replays requests.** Only connection failures are retried, the proxy timeout is above the server's long-poll cap, and `GXMCP_HTTP_TOKEN` is forwarded, so a keyless mutation cannot run up to three times and a token-protected master no longer answers 401.
- **In-flight requests are drained on shutdown.** On stdin EOF the Gateway waits up to 10 s for in-flight requests before stopping workers.
- **`DispatcherException` is logged.** The envelope's hint pointed to worker logs that contained nothing; the full exception chain is now logged with method, action and correlation id.
- **Launcher lifecycle and startup.** The launcher forwards termination signals to the Gateway and kills it on exit, uses an existing `~/.genexus-mcp/config.json` without paying the GeneXus registry discovery, and adopts a `config.json` from the working directory only when it looks like a GeneXus MCP config.
- **gxwire cache writes are atomic,** and gx-engine refuses a `sqlcmd -Q` statement that would exceed the 32,767-character Windows command-line limit with a clear message instead of an opaque OS error.
- **nexus-ide webviews.** History, Index, Properties and Structure use a per-render script nonce instead of `'unsafe-inline'`, MCP-supplied text is HTML-escaped, and webview messages are validated before reaching MCP calls. This also fixes Structure handlers that referenced an undefined variable and a Properties panel that stacked message handlers bound to earlier objects.
- **Compact tool summaries no longer end on a dangling word.**
- **`genexus_create` says at the top of the result when the object was not placed where it was asked.** With `module=` naming a Folder (or `folder=` naming a Module) the object was created in the Root Module and the answer was a plain `ObjectCreated`; the refusal (`DestinationKindMismatch`) was only inside `placement.detail`, with a hint about a `destKind` argument the caller does not have. The result now also carries `placementApplied: false` and a `warnings` entry that says where the object really is and, for a kind mismatch, names the parameter to use (`folder=` or `module=`). A move that fails for any other reason gets the same entry with the SDK's reason.
- **`genexus_transfer` `import` of a Web Master Panel no longer ends in `TransferImportFidelityFailed` with the object deleted.** The SDK exports a form without the ids of its layout containers and with the images and variables of its controls by name, and it generates the ids and resolves those names to local keys when it stores the imported form. The check that follows the import found those differences on every master, read them as a lost write and removed the object it had just imported (the SDK itself reported the import as successful). An `id` that the imported form carries where the package's form has none, an image named in the package and held by key (`<guid>-<Module.Name>` against `<guid>-<int>`) and a variable named in a custom property and held as `var:N` are no longer differences; a different `id`, an `id` the import dropped, a name the SDK did not resolve and every other attribute, control or text still are.
- **A refused `genexus_transfer` `import` keeps its evidence in the default (terse) error.** The refusals (`TransferImportFidelityFailed`, `TransferImportDeclined`, `TransferImportFailed`, `TransferImportVerificationUnavailable`) answered with their code, message and hint: the SDK's own messages and, for a fidelity failure, the object whose WebForm did not survive the import, the difference found and how the repair and the rollback ended were only in the verbose error (`verbose_errors=true`). The terse error now also carries `imported` (absent when the outcome is unknown), `sdkDiagnostics` (an empty list means the SDK said nothing; `diagnosticsAvailable=false` means it has no output service) and, where the refusal has them, `fidelityVerified` and `fidelity`. The lists are capped at 20 messages (errors first, then warnings) and 10 mismatches and each text at 500 characters, with `sdkDiagnosticsTotal`, `mismatchesTotal` and the matching `...Truncated` flags saying what was cut; a repair write is reduced to `repairStatus`, `repairCode` and `repairMessage`. `verbose_errors=true` still returns everything.

### Internal

- Split `DispatchToolCallCoreAsync` into stage methods (`Program.ToolDispatch.*.cs`) and moved the `WriteObjectInternal` success envelope into `BuildWriteAppliedResponse`; no behaviour change.
- Removed unused code: the Gateway middleware pipeline and `DiagnosticAndHealingEngine`, the Worker `MultiObjectUnitOfWork` helper and `WritePipeline.PreWriteSnapshot`, and the gxwire `memmap2` and `rayon` dependencies.
- CI also runs on pushes to `main`, runs the Python metadata, manifest and replay unit tests in the contracts job, and audits both Cargo lockfiles with a SHA-pinned cargo-audit. The Rust toolchain is pinned to 1.97.1.
- Stopped tracking files that `.gitignore` already excludes and two committed `.trx` test results; trimmed `AGENTS.md` to under 200 lines by moving task-specific guidance into the linked documents; moved releases older than v4 into `docs/changelog/`.
- Gateway logging no longer stats the log file on every line, and failed SDK transaction rollbacks in the write path are logged instead of silently swallowed.

### Added

- **`genexus_db` `records_query` reads Db2Universal / DB2 for IBM i datastores (including `dataStoreAlias`).** Any `records_*` call on a DB2 datastore failed with `DataStoreProviderUnsupported`. The DB2 DBMS codes and JT400/DB2 provider names now map to a `db2` dialect: `FETCH FIRST n ROWS ONLY` paging, positional `?` parameters and uppercase double-quoted identifiers over the datastore library. `sample_data`, `drift_check` and `sql_navigation` do not depend on the dialect (their plans stay `planUnavailable`). `records_insert`/`records_update` are refused on DB2 with `DataStoreWritesUnsupported` before any connection is opened. The Worker cannot load the JT400 JDBC driver, so querying needs an IBM ADO.NET provider (`IBM.Data.DB2.iSeries` or `IBM.Data.DB2`) registered on the Worker host (either IBM ACS or the `IBM.Data.DB2.iSeries` NuGet package registered in `DbProviderFactories` / `App.config`); without one the answer is `DataStoreProviderUnavailable` naming both options. When the KB's DB2 datastore leaves connection properties empty (e.g. runtime-configured / JNDI datasource), `records_query` now accepts a read-only `dataStoreAlias` with `family: "db2"` (`database` optional for IBM i, `integratedSecurity` defaulting to `false` so host credential environment variables are required). Not tested against a real DB2 server. https://github.com/lennix1337/Genexus18MCP/issues/959
- **`genexus_edit` writes a whole part from a file with `contentPath`.** A full-part write took its text only inline, in `content`, so a caller that goes through a command line could not send a large one: a 290 KB Design System style source does not fit in the roughly 32 KB a Windows command line takes. `contentPath` is the fully qualified absolute path of a UTF-8 file (up to 1 MiB: the routed command carries the text twice and a shared-host Worker takes one 4 MiB frame; a larger part goes through `genexus_io import_part` with `inputPath`) whose text replaces the part; it is read as it is (line endings and a final newline stay, a UTF-8 byte order mark is dropped) and routed exactly as an inline `content` would be, so the preview, the version check and the write are unchanged. It cannot be combined with `content`, `patch`, `operation`, `context`, `ops`, `targets`, `parts` or `changeSet`, nor sit inside a `targets[]`, `parts[]` or `changeSet` item, and a bad file is refused with `ContentPathInvalid` (also for a named pipe, a device or anything else that is not a regular file; those are never opened), `ContentPathNotAbsolute`, `ContentPathNotFound` (also for a directory), `ContentPathUnreadable`, `ContentPathTooLarge`, `ContentPathEmpty` (clearing a part is asked for with `content=""`) or `ContentPathNotUtf8`, each saying that no write was attempted. With an `idempotencyKey` the file's SHA-256 is part of the request, so the same key over a rewritten file is an `IdempotencyConflict`, as it is for a different inline `content`.
- **`genexus_transfer` `export` and `inspect` accept `async=true`.** A large Design System exported with `includeDependencies` can run for minutes on the Worker's one SDK thread; called synchronously it left the caller with no handle once its own window expired, while every other call answered `WorkerBusy`. With `async=true` the call returns `operationId` and `pollTarget` before the SDK call starts, and the outcome stays readable with `genexus_lifecycle action=status` / `result`, like the version-store reads (`action=cancel` marks the operation cancelled, but an export already running in the SDK cannot be interrupted and still writes its file). `import` mutates the Knowledge Base and stays synchronous.

### Changed

- **`genexus_io export_part` says what it wrote.** Besides `bytes`, the answer now carries `sha256` of the exact bytes (UTF-8, no BOM), `lines`, `lineEnding` (`CRLF`, `LF`, `CR`, `mixed` or `none`), `endsWithNewline`, the part's `versionToken` and `tokenFingerprintMatchesFile`. For a text part (a Procedure `Source`, a Design System `Styles`) the token's last segment is the SHA-256 of the part text exactly as the SDK holds it (the MCP normalises nothing; on GeneXus 18 U16 the SDK itself keeps those parts with LF line endings, so a CRLF file written into one reads back as LF), so it equals the `sha256` of the exported file and `tokenFingerprintMatchesFile` is true; for a part whose token is built another way (an External Object) it is false. A hash taken after adding or trimming a final newline does not match, and the help now says so.

### Fixed
- WorkWithPlus `add_grid` (variable grids and SDT collection grids) and `add_grid_variable` now handle default-named `<grid>` elements, omitted default variable attributes (`Numeric`, `basicLength`, `basicDecimals`, `basicCLength`), and WorkWithPlus `DropDownValueOptionCustomType` resolution across loaded assemblies: `VerifyVariableGrid`, `FindVariableGrid`, `FindRequestedGrid`, and `ResolveNativeGrid` match an unnamed `<grid>` as `"Grid"` (matching `ContainerLabel`/`NativeContainerLabel`), `VerifyVariableGrid` accepts omitted pattern-default column attributes, and `SetNativeDropDown` converts via `PatternInstanceElement.Attributes.ConvertPropertyValueFromString<StringStorage>` with a loaded-assembly fallback for `DropDownValueOptionCustomType`. Not tested against a live WorkWithPlus KB. https://github.com/lennix1337/Genexus18MCP/issues/961
- `genexus_wwp` `add_table` and `move_control` now convert string attributes through `PropertiesObject.ConvertPropertyValueFromString<StringStorage>` before writing via `ChangeAttributeValueCommand` (preventing `InvalidCastException` to `DropDownValueOptionCustomType` when WorkWithPlus reads `themeClass` on `textBlock`/`table` children), and no longer fail with `WwpProjectionNotConfirmed` when targeting derived Transaction sections (`selection`, `extraSelection`, `view`, `prompt`, `tabularTab`, `gridTab`, `webComponentTab`) whose WebPanels are updated by `regenerate_derived` rather than the parent Transaction's `WebForm`. https://github.com/lennix1337/Genexus18MCP/issues/890
- `reorg_preview`/`reorg_impact`: the IDE's migration history (`<Environment>\migrations\default\V*__migration.sql`) now counts as the last reorganization. The SDK's `lastReorg` can be years old, so `reorgLikelyNeeded` was always true; with deep analysis, a `ReorganizationNeeded` without DDL after a newer migration is reported as `verdictEvidence.state = InSyncByMigrationHistory` (`reorgNeeded` keeps the SDK verdict) https://github.com/lennix1337/Genexus18MCP/issues/928
- WorkWithPlus writes (add_grid, add_grid_variable, form actions, layout, grid attributes) that fail and roll back exactly no longer report `partialPersistenceDetected: true` next to `persisted: false`; the flag stays true only when the state was not restored (#961).

- **`genexus_doctor kb=<alias>` describes that KB, not the gateway's default.** With a GeneXus 9 KB named explicitly, the top-level `geneXus` block showed the gateway's GeneXus 18 installation and the `kb` block another KB, while only `worker.diagnostics.configured` named the GX9 one, so the global context could not be told apart from the target worker's. Now the `kb` block follows the `kb` argument, the `geneXus` block describes the target KB's own installation (`source: "kb"`, `driver`, `major`; the gateway's installation moves to `geneXus.gatewayDefault`), a legacy `com-gxpublic`/`dotnet-reflection` KB reports `sdkCompatibility: not_applicable` instead of being checked against the gateway's .NET SDK, and a new `target` block says which KB was diagnosed, whether its worker is usable and the next step. A worker stuck in `starting` now reports `elapsedSeconds`, `lifecycleState`, its last startup diagnostic and, after 120 s, `stalled: true` with the reload command, instead of "retry in a few seconds" forever. The answer also carries `issueReport`: versions, driver, worker state and causes with drive/UNC paths, aliases and credentials removed, ready to paste into an issue. https://github.com/lennix1337/Genexus18MCP/issues/965
- **The Worker now starts and answers on a GeneXus 8.0/9.0 (`com-gxpublic`) installation, which has no .NET SDK.** It used to die in `Main` with `Could not load file or assembly 'Artech.Architecture.Common, Version=11.0.0.0'` right after logging "Starting in legacy driver mode": building the command dispatcher eagerly created SDK-only services (pattern apply, save-as, visual structure), and the first `read`/`write` command resolved SDK types in the write-destination guard and the read handler. Those services are now built on first use, the COM read path no longer shares a method with SDK code, and a pinned write destination is refused on the COM driver without loading the SDK. A regression test runs the real Worker against a folder with no `Artech.*` assemblies. Real GeneXus 9 was not available to verify. https://github.com/lennix1337/Genexus18MCP/issues/965
- **`genexus_read part=WinForm` returns the whole form, and `genexus_edit` can write it.** The WinForm part of a WorkPanel came back as `<Properties />` with `patchable:false`, hiding the Form, Canvas and every control (including the text forms of a Cobol generator). The read now returns the part's own serialized Document (`Document/Form/Type/Class/ClassGuid/SizeUnit/Info/Canvas/Elements`, an untouched default form expanded to the default Windows form). `genexus_edit part=WinForm mode=full` accepts that same XML (a `<Part>` or bare `<Document>` root) and applies it with the importer an XPZ import runs, inside a KB transaction: a `<Form>` the SDK would silently ignore (missing or unknown `<Type>`, bad `<ClassGuid>`, wrong part type) is refused as `WinFormXmlInvalid`, `dryRun` validates without touching the part, `baseVersion` is enforced, and success is confirmed by reading the part back from a freshly loaded object; a failed write restores the previous form. https://github.com/lennix1337/Genexus18MCP/issues/963
- `genexus_structure update_visual` and `genexus_edit part=Structure` now persist added attributes and levels on a multi-level Transaction (https://github.com/lennix1337/Genexus18MCP/issues/955). The DSL reader stripped the indentation of the first line, so every level attribute was read as a root attribute and the level was rejected as empty; levels are now delimited by their braces and by indentation (tabs count as 4 spaces). `update_visual` now creates a requested attribute that does not yet exist in the KB (it used to skip it silently, so the save never matched the request), reports every member the SDK refused with the SDK message instead of swallowing it, adds the validator's detail to a failed save, and `StructureUpdateNotPersisted` names the members that differ.
- `force=true` now lets a write proceed over another owner's unexpired operation lock in the default isolated mode too. The write path read the `AlreadyHeld` refusal code only from the top level of the lock reply, where it never is (it sits under `error.code`), so the force exemption only worked in the shared-host Worker child and an isolated forced write was refused with `AlreadyHeld`. The holder's lock is still left untouched, a write without `force` is still refused, and a stale base version token still rejects the write with `StaleObject`. https://github.com/lennix1337/Genexus18MCP/issues/958
- A Knowledge Base the Worker could not open is now reported to the MCP client instead of leaving every later call on `IndexNotReady`. The Worker keeps the last open failure (code, message, path, time) and returns it in its index state; the Gateway answers KB-bound tools with `KbOpenFailed` and the SDK message, shows it as `index.kbOpenFailure` in `genexus_whoami`, and `genexus_kb action=open` returns it (waiting up to 2 s for the Worker's own open, then cancelling the probe so it leaves no pending request behind) instead of `opened`. A successful open clears it, and a new open drops the failure of an earlier attempt. A Worker command whose caller is cancelled no longer leaves its pending entry in the Gateway. https://github.com/lennix1337/Genexus18MCP/issues/957
- In the opt-in `shared-host` mode, the process checks below found and fixed three Worker host defects. Two Gateways that open the same KB at the same time now both attach to the elected Worker host: the host replaces its registry v2 record with one `MoveFileEx` rename, retried while a reader holds the file, instead of `File.Replace`, during which a concurrent reader found the record absent and refused the open with `KB_WORKER_OWNED_ELSEWHERE` / `liveness-unverified`. The stale-ownership recovery log now names the real reason when it removes an `isolated` record without stopping a process (`owner-not-running` or `start-time-mismatch`) instead of `orphaned-worker`. A Gateway whose Worker host refused the Worker start (for example `KB_POOL_FULL` / `low-memory`) now gets that typed refusal on the next registry poll instead of waiting `AttachReadyTimeoutSeconds` (120 s by default) for `SHARED_WORKER_ATTACH_FAILED` / `readiness-timeout`. https://github.com/lennix1337/Genexus18MCP/issues/854
- **A style source that points at an Image object the Knowledge Base does not have is refused with a reason.** The SDK refuses a Design System (or StyleSheet) source with `gx-image(Name)` for a missing Image, but its public validation throws the reason away, so the write answered only "Theme/StyleSheet write failed" with a hint to rewrite a source that was fine. `genexus_edit` and `genexus_io import_part` on a `Styles`/`StyleSheet` part (`dryRun` included) now ask the part to validate again into a collector of their own and return what the SDK said in `sdkMessages`, and when its message confirms that a referenced Image object is missing they answer `ThemeStyleUnresolvedReferences` with `unresolvedImageReferences` (every missing name once, in order of appearance; the SDK names only the first). When the SDK reports something else, such as a syntax error, or nothing the MCP can read, the missing images are still listed in `unresolvedImageReferences` beside the SDK's words and the code stays `ThemeStyleApplyFailed`. The style part itself is not touched and nothing is written in either case.
- **A declined XPZ import names the Image objects the package refers to and nobody has.** `genexus_transfer action=import` of a package whose Design System or Theme points, through `gx-image()`, at Image objects that are neither in the package nor in the Knowledge Base made the SDK's `ImportFile` return false with no diagnostic. The `TransferImportDeclined` answer now lists them in `unresolvedImageReferences` and its hint says to import or create those images first.
- A fixed-size variable dimension that the SDK accepts but does not keep now says what was requested and what the variable reports (`requested dimensions=2 sizes=[4,5]; the variable reports dimensions=2 sizes=[1,5]`) instead of only "did not retain the requested values".

### Internal

- The shared-host process check `Long_operation_on_one_kb_does_not_delay_probes_to_another_kb` no longer fails when one of its two opens returns before its connection has learned the Worker's pid. Cold_Start admission starts one Worker at a time by default, so when the test opens two KBs at once one start is held until the other ends. `ConnectV2` returns as soon as the registry record is Ready, but the broker's `worker_restarted` frame that names the Worker is applied later by the connection's read loop, so the open reply could still be the earlier acknowledgement (`state` `held`, `workerPid` 0) and the test failed on its `workerPid > 0` assertion. The test now reads each KB's Worker pid from the broker's live status, the pid the probe responses are compared against, and requires an open reply that does name a Worker to name that one. With the test process limited to two CPU cores the old assertion failed in 12 of 12 runs and the new one passed in 12 of 12.

A Worker started by the host checks its `SingleInstanceLock` by PID and process start time, so a lock left by a crashed Worker or a reused PID no longer blocks startup. The host detaches attachments whose Gateway process has exited within 10 seconds, so the Worker idle timeout starts once the last live Gateway is gone. - **WorkWithPlus pattern edits keep the host and its parent WebForm in one SDK transaction.** Neither object is committed until a fresh read of both confirms the edit. A failed parent save returns the SDK validation diagnostics and rolls the transaction back before commit, instead of reporting success after a parent save that was not verified.

- **A failed WorkWithPlus projection no longer issues a compensating text write.** Restoration is checked by independent re-reads of the host and parent XML and of their object snapshots.
- **A WorkWithPlus edit is no longer accepted when the parent WebForm cannot be read back as projected.** An existing visual part that cannot be read is an error, not a match, and a parent without a visual part is compared by its absence.

- **Source searches and inspections see the saved source after a WorkWithPlus edit.** The index and cached source of the host, its parent and their names are refreshed after a projection write.
- **Structural ids that the SDK recreates in native WebForms no longer make a correct projection look changed.** Ids that no layout element references are compared as the same structure.
- **`genexus_wwp add_grid_variable` shows what the WebForm holds when it refuses a write.** A refused write (`WwpProjectionNotConfirmed`) used to answer with only a count of the grid controls. The reply now carries `webFormProjection`: the names of the grids the form holds (`webFormGrids`) and, only when exactly one grid matched the requested name, that grid's `columns`. When no grid matched, `columns` does not come: only the names in `webFormGrids` do, and that list is empty when the form has no grid control. Lists longer than 50 entries are cut to 50, with their totals. The verbose reply already had it. Refs [#638](https://github.com/lennix1337/Genexus18MCP/issues/638).
- **A protected Events save no longer fails because another process saved a different object.** `genexus_edit part=Events mode=patch requireObjectSave=true` proves that it wrote nothing but the target by comparing three whole-KB inventories, and any other object that differed failed the operation with a generic `ObjectSaveIncomplete`, even when the Events source had been committed and read back (before the commit it rolled the save back instead). On a large KB each inventory takes about a minute (an estimate), so a developer saving anything in the IDE during those minutes was enough. The save now compares the SDK stamp of each differing object with the interval in which the save itself writes, calibrated on the target's own new stamp: an object that another process saved once, outside that interval, is listed in `concurrentChanges[]` and does not fail the save. Anything else still fails as before (a stamp inside the interval, two saves of one object, an object created, deleted, moved or renamed, or no calibration), and the failure now names the objects (`unexpectedChangedObjectDetails[]`), says that the target itself is verified (`writeVerifiedForTarget`), carries `reasonCode: OtherObjectsChangedDuringSave` and a one-line message instead of the generic one. `otherObjectMetadataIntact` and `rollbackVerified` now mean "no object in doubt", and the default (terse) error projection keeps these fields. A save refused before the commit keeps naming the objects that caused the refusal in `preCommitUnexpectedChangedObjects` and `preCommitUnexpectedChangedObjectDetails[]`, also when the rollback undid their change and the final fields show a clean Knowledge Base. See `docs/events-object-save-isolation.md`. [#741](https://github.com/lennix1337/Genexus18MCP/issues/741)

- **`genexus_create` refuses a WorkWithPlus template by name, before any lookup, in every mode.** A `type` that names a WorkWithPlus template (`WorkWithPlus for Web Template`, `WorkWithPlusforWebTemplate` or `WWPTemplate`, in any case and with any white space) was looked up in the SDK type table and refused with `UnsupportedObjectType`, and the hint did not say where a template is created. The refusal now runs first on both create methods, and the hint reads: `A WorkWithPlus template is created and edited in the GeneXus IDE (WorkWithPlus Settings Editor); genexus_create neither creates nor updates it.` With `object_atomic`, the refusal sits in the spec, so `mode=create`, `mode=update` and `mode=auto` all refuse a template: an existing template cannot be updated through `object_atomic` either. The supported-type list in the hint, previously labelled `Known types:`, is now `Supported types:` and includes `Module`, `Folder` and the types that resolve only through ObjClass. Refs https://github.com/lennix1337/Genexus18MCP/issues/793
- **The `genexus_create` schema type list names `DesignSystem`.** The create already saves an empty DesignSystem through the same SDK path as the other object types, but the schema type list left it out. The help and the `NoDesignSystem` hint now say that a DesignSystem is created with its parts empty (Documentation, Source, Styles, Tokens). Refs https://github.com/lennix1337/Genexus18MCP/issues/793

It is read-only: nothing is restored or saved, and `async: true` works as on the other version-store reads. Parts that are not plain text are compared too: Variables as their declarations, WebForm/Layout as their editable XML with the ids the SDK regenerates on every read masked, and any other stored part as the SDK's serialized XML, re-indented so the diff is per element. A pattern projection part the SDK does not store is refused with `VersionPartNotExtractable`, and a part too large for an in-process diff with `VersionDiffTooLarge`. The tool schema budget grows by about 50 tokens (all profile 103000 -> 103100 bytes, devops 52500 -> 52600) for the new action value and the `toVersionId` input; the `versionId`, `async` and `context` descriptions were shortened to offset part of it. https://github.com/lennix1337/Genexus18MCP/issues/710

The `dotnet` lane no longer rebuilds gxwire on every run (the binary is cached by its sources), no longer builds and runs the MCP smoke contract test a second time, and skips the 300 MB .NET SDK download when the runner already has a 10.0 SDK. The release script suite runs its scripts in parallel, the `contracts` lane no longer repeats four of them, and the CI policy's lane-evidence scan is compiled (20s to 4s). The Rust lanes drop a release build nobody used, and gx-engine runs its tests with `cargo nextest`, in parallel across its ~90 test binaries. The `test` gate runs on Linux. Guardrails keep it fast: every job has a `timeout-minutes` ceiling, a Gateway test over 10s or a release script over 120s fails CI unless `scripts/ci/test-time-budget.json` lists it with a reason, and nextest kills a gx-engine test after 120s. `CODING_STANDARDS.md` → CI time budget has the rules.

- **`genexus_edit` previews of a complete Events save (`requireObjectSave`, `dryRun=true`) say whether they can be applied.** A preview keeps `status: ok` / `code: Applied` because the textual simulation succeeded, which never meant permission to write. It now also returns `canApply`, `applyBlockers[]` (every independent reason it cannot be applied, each with `code`, `layer`, `message` and `remediation`: missing pins, an unaudited SDK bundle, no `baseVersion`, no match, an indentation check the real write would refuse), `previewSummary` and `writeAttempted: false`, and its `details` no longer reads as a clean success when the save is blocked. Pins never make a bundle eligible, there is no allowlist by version number, and `blocker` and `reason` keep their meaning, except that for a destination refusal `reason` is now a plain sentence (its code is `reasonCode`) instead of the serialized guard envelope. The terse error projection keeps `reasonCode`, `blockers[]` and the pin evidence.
- **Pin diagnostics say which pin variable reached the Worker.** `effectivePins.variables` reports each of `GXMCP_EXPECTED_KB_PATH` and `GXMCP_EXPECTED_KB_VERSION` as `absent`, `blank` or `present` (the KB path appears only as an identity hash and the version by name), and `effectivePins.source` says they are read from the process environment, so a pin that was written but never reached the Worker is visible. An eligible preview carries the same pin evidence as a refusal, and so do the destination guard's own `WriteDestination*` refusals. `profileRevision` stays the revision of the Gateway configuration file.
- **The receipt of an applied Events no-op says `noContentChange: true`.** An identical source applied with `requireObjectSave` still runs the guarded save (the revision advances, the content hash does not), so `writeAttempted` and `objectSaveInvoked` stay `true`; the receipt now carries `noContentChange` next to `idempotent` and `sourceChanged: false`, as the preview already did.
- **A patch that fails to match because of an undecoded line break says so.** When the patch text carries the two characters backslash and `n`, `r` or `t` and the source does not, the `NoMatch` failure also reports `literalEscapeSequences` and a `literalEscapeHint`. The text is still matched exactly as sent: nothing is converted or retried.
- **A refused isolated Events save no longer says that only a U16 build is accepted.** `SdkBundleNotAudited` now reads "requires a complete audited SDK bundle", `evidence.auditedBundles` lists the complete-bundle ids next to the two U16 build ids, the `genexus_edit` help and `docs/events-object-save-isolation.md` drop the U16-only wording, and a failed bundle audit is reported as `SdkBundleAuditFailed`, naming every unknown loaded assembly at once ([#734](https://github.com/lennix1337/Genexus18MCP/issues/734)).
- **A real `genexus_properties action=move` needs `baseVersion`.** Without the `versionToken` of the object as last read (from `get`, `genexus_read` or a `dryRun`) the move is refused with `BaseVersionRequired`, which hands out the current token; a stale token returns `VersionConflict` before anything is written and again inside the transaction. `dryRun` does not need the token and returns it, and `expectedVersion` is accepted as an alias. `genexus_properties action=set propertyName=Folder`, which has no token of its own, still moves against the version it just read.
- **`genexus_properties action=move` and `genexus_create action=object_atomic` take a name, a path or a GUID as the destination and say what they resolved.** `Root Module/<Module>/<Folder>` (with or without the `Root Module` prefix) resolves segment by segment; a name shared by several Folders or Modules is `DestinationAmbiguous` (listing the path and GUID of each) instead of silently using the first one found; a Module asked for as a Folder is `DestinationKindMismatch`; a path that does not exist is `DestinationNotFound`, naming the segment where it stopped and what is there. Receipts carry `fromPath`/`toPath`, the resolved `destination` and, for a move into another Module, `moduleChange`.
- **A move that fails says why, and proves the rollback.** `MoveFailed` carries `reasonCode` (`SdkPersistRefused` with every persist path that was tried, `ParentNotPersisted`, `ContentChangedInTransaction` with `propertyDifferences`, `TransactionFailed`), `phase`, `expectedParent`/`actualParent` and a `rollback` that is `verified` only when a fresh read (SDK caches invalidated, resolved by GUID) finds the original parent and every part restored. These fields now survive the terse error format. A successful move reports `verification` (fresh read, position, parts compared) and the object's `identity`; an object that already is in the destination returns `ObjectAlreadyInDestination` and writes nothing. After a Folder or Module moves, the cached copies of the objects inside it are dropped and their index paths refreshed.

The declared type now comes from the property descriptor when the value is unset, and types with a string `TypeConverter` are converted through it ([#701](https://github.com/lennix1337/Genexus18MCP/issues/701)).
- **A request that arrives while an idle Worker is being stopped now runs on a replacement Worker instead of failing with `-32603 crashed/exited`.** The idle reaper stops the Worker once nothing is queued. A request accepted between that check and the pool dropping the Worker was queued on a stopped writer. Nothing sent it, and the exit then aborted it as a crash. The Gateway now records which commands have not started to be written. A Worker that is already stopping refuses new commands. A command that never reached the Worker is sent to a replacement at most twice, mutating tools included, because the old Worker cannot have run it. A command that was delivered but never answered is not re-sent: its error carries `data.dispatchState=delivered-unanswered` and `reconcileRequired=true`, so the caller reads the target back first ([#692](https://github.com/lennix1337/Genexus18MCP/issues/692)).
- **In strict resolution, a call without `kb` after an idle Worker exit now uses the KB that was opened and respawns its Worker.** The idle exit removed the KB from the set of live Workers. With no Worker left, the resolver answered `No Knowledge Base is open` in 1–2 ms and never started a replacement. `whoami` also reported the KB as unselected. A KB opened in this Gateway is forgotten only by an explicit close, so when no Worker is live the resolver now counts those KBs as the open set. One such KB resolves as `single-open`, a conflicting configured default still yields `DefaultConflict`, and several yield `KB_AMBIGUOUS` ([#692](https://github.com/lennix1337/Genexus18MCP/issues/692)).
- **A `genexus_layout` read issued right after a Worker (re)opens its KB no longer runs alongside the index delta refresh inside the SDK.** The first `get_tree` after an idle respawn was dispatched in the same millisecond as the post-open delta refresh. It failed with `LayoutReadException` ("exception thrown by the target of an invocation"), and the same call succeeded later. The delta-refresh thread read `DesignModel.Objects` (`GetKeys`, `Get`, and the catalog reconciliation) without `SdkGate`. Layout reads did not take the gate either. Only source reads did. The delta refresh now reads the SDK inside `SdkGate`, one object at a time. `get_tree`, `find_controls` and `inspect_surface` hold the gate for their dispatch, so they wait for the current object instead of loading parts beside it ([#692](https://github.com/lennix1337/Genexus18MCP/issues/692)).
- `genexus_layout get_tree` failures report the SDK exception that caused them, with `exceptionType` and `failureTrace`, instead of the reflection wrapper's generic "target of an invocation" message. The cause is also logged as `[LAYOUT-READ]`. The Gateway's `TOOL-LATENCY` line and tool statistics now count a Worker envelope with `status=error` or `isError=true` as `result=error`, not `success` ([#692](https://github.com/lennix1337/Genexus18MCP/issues/692)).
- `genexus_lifecycle build_all` keeps the SDK event broker enabled during the task and restores its prior state afterwards, including failures. The external MSBuild template also enables SDK events. This allows SDK-configured pre/post-build commands to receive their normal events; Build All is refused during SDK write-event isolation ([#696](https://github.com/lennix1337/Genexus18MCP/issues/696)).
- Build All results expose `buildEvents.policy=sdk` and `buildEvents.executionVerified=null`, including compact responses: build completion does not independently confirm configured shell commands or their external effects. Live command execution still needs separate evidence. Failed/invalid SDK task returns and missing entry points now emit diagnostics to the build output; missing-completion guidance requires reconciliation of configured command effects before any retry.
- `genexus_layout delete_printblock` propagates a failed layout reload instead of reporting a verified deletion when the saved object's layout could not be read ([#692](https://github.com/lennix1337/Genexus18MCP/issues/692)).
- **`genexus_layout` `add_printblock`, `rename_printblock` and `delete_printblock`, and `genexus_create` (`ObjectCreated`), say whether the store holds the change.** The check after the commit read back through the instance the write had just changed, so a success could not tell "saved" from "only in this Worker's memory", and a Worker that exited afterwards (for example on its idle timeout) could take such a change with it without any error having been returned ([#692](https://github.com/lennix1337/Genexus18MCP/issues/692)). The check now reloads the object with the SDK cache invalidated and resolves it by identity, so a change the store does not hold is refused as `AddPrintBlockVerificationFailed`, `RenamePrintBlockVerificationFailed` or `DeletePrintBlockVerificationFailed`, and the result carries `saved` and `persistedVerified`: `true` only when the reload found the change, `null` (never `true`) with `verification` giving the reason when the reload was unavailable. The Worker log no longer calls a change "staged in memory" when the caller saves it right after. The data loss on idle shutdown reported in the issue was not reproduced and its cause is still open; this makes such a loss visible at call time.
- **`genexus_wwp` `add_grid_variable` writes again**, now with a projection check that proves the requested column rather than any change. v4.0.3 refused every write as `WwpProjectionVerificationUnavailable` because the earlier check accepted a parent WebForm that had merely changed. After the PatternInstance re-read confirms the column, its position and the untouched siblings, the WorkWithPlus projection must leave the parent WebForm with exactly one new column of the grid control that renders the requested grid (`controlName` = the grid's name) bound to the variable, as the SDK stores it (`attribute="var:N"`, N being the variable's id in the parent, or `&Name`). A WebForm that is unchanged (as observed without a Design System), changed elsewhere, holds the variable outside that grid or already held it is refused as `WwpProjectionNotConfirmed` and the PatternInstance and WebForm snapshots are restored; the result carries `webFormProjection` with the grid's columns as the form holds them ([#638](https://github.com/lennix1337/Genexus18MCP/issues/638)).

- **`genexus_query` `fields` sent as text.** A client whose schema did not declare `fields` sent `["name","type"]` as a string, the comma split cut it into `["name"` and `"type"]`, every result was projected to an empty object and a type-only query never reached gx-engine. `fields` is now declared as an array of strings in the input schema, so clients send the array, and a text value holding a JSON array is read as that array when the result is projected. The engine route still requires the array form: a JSON array sent as text stays on the SDK. https://github.com/lennix1337/Genexus18MCP/issues/637
- `genexus_wwp add_table` no longer lists the new table in the container's `childrenOrderedList` with the transaction's table code (`01`) on a WebPanel, whose WorkWithPlus instance lists tables as `7;66;...`: with no sibling table to copy the code from, the entry now takes the code the container (then its ancestors) is itself listed with. `WwpTableNotPersisted` also reports what the re-read container holds. - `genexus_wwp add_grid_variable` accepts the identity a client can obtain: the variable's own GUID plus `-Name` from the owning object's Variables part. The old lookup asked the KB for an object with that GUID, which a variable never is, so no reference was ever accepted. `genexus_wwp action=list` returns `variables[].variableReference`, and the identity refusals return `expectedVariableReference` / `declaredVariables` ([#638](https://github.com/lennix1337/Genexus18MCP/issues/638)).
- **WorkWithPlus typed writes save the object that owns the edited part.** With the Transaction or WebPanel that hosts the pattern as target, the SDK hands out one copy of the WorkWithPlus object per resolution, and the PatternInstance part belongs to the copy the envelope was built for. `add_table`, `set_table_type`, `add_tab`, `move_control`, the grid column actions and the Web Component replacement resolved the part from the requested host while saving the instance they had read, so the save left the change out. On a real WorkWithPlus package (16.2, Transaction host) `add_table` ended in `WwpTableNotPersisted` every time and `set_table_type` in `WwpTableTypeNotPersisted`, while a target naming the `WorkWithPlus<Name>` object itself worked. Every typed write now takes the part from the instance it saves, as `add_grid` and the form user action already did. When the re-read still lacks the table, the refusal states how many tables the plan expected, how many the re-read contains and their names, so a dropped table can be told from a renamed one. https://github.com/lennix1337/Genexus18MCP/issues/638
- **WorkWithPlus `add_table` with `includeInPanel` or `panelTitle`.** The pattern declares `includeInPanel` as a boolean, and the table was created with the text `True`: the package failed with an `InvalidCastException` when the table element read the property back, so a panel table was refused even after the previous fix. The boolean itself is stored now, together with its default twin.
- **WorkWithPlus `move_control` between two tables.** The control was detached with `RemoveElementCommand` and added with `AddElementCommand`, which leaves its parent on the old table, and the SDK refused the add ("'textBlock' cannot be added as child of 'table'"). The control now changes table through `PatternInstanceElement.MoveElement`, and a requested position or `before`/`after` is applied afterwards. Moving a control inside one table is unchanged. Verified on a real package for text blocks, with and without a position; moving a `variable` or an `attribute` still ends in `ControlNotFound` there, because the native lookup reads the attribute reference through the property bag, which returns the CLR type name, and expects the element type `attribute`, which the package names `TrnTableAttribute`.
- **Docs: what is verified for `add_table` and `move_control` on a real WorkWithPlus package.** The tool help and the capability inventory said neither was verified; they now state what was verified (new tables, panels, text-block children and moves), what is not (attribute and variable moves, attribute children, and `add_tab`, which ends in `WwpTabNotPersisted` on the package tested) and that a WebPanel host without a Design System persists the instance but is rolled back as `WwpProjectionNotConfirmed`.
- **`genexus_apply_pattern reapply=true` on an existing WorkWithPlus instance** returned `PatternApplied` while only the parent was re-projected: the derived objects, such as the `LoadDVCombo<Trn>` helper, kept the contract they had before the instance changed. The response now carries `derivedObjectsRegenerated` (false for a reapply) with a note naming `regenerate_derived`, and `mode=diagnose` no longer says that reapply regenerates them.
- `gx-engine rebuild-all --object <Name> --closure` on an object the closure does not target (for example a non-main Procedure nothing reaches) no longer emits a project without a `Main` that fails to compile with `CS1555`: nothing is emitted or compiled, the report is `partial` (exit 3), and its warning says the entry is listed in `not_targeted_objects`. https://github.com/lennix1337/Genexus18MCP/issues/675

An observed version change, lost snapshot or failed recheck requires reconciliation, never successful output or automatic SDK replay. Successful Worker snapshot refreshes publish atomically; failed refreshes still clear the snapshot. Snapshot requests reserve only an existing ready Worker, with a two-second send/response budget and no acquisition, respawn or SDK-startup wait.

- **`genexus_connection_recover action=recovery_read_complete`** clears a `PostTimeoutReadRequired` fence from a certified SDK read that is never returned, so a part larger than the response budget (above 200000 characters of `source`) is no longer stuck behind its fence (https://github.com/lennix1337/Genexus18MCP/issues/615):
  - The Worker re-reads the fenced part fresh from the SDK, whole (offset 0, every line), and builds a small certificate (`gx-recovery-read/1`: object identity, SDK coverage, `totalLines`, `sha256`, `versionToken`, per-target write stamp) before any pagination, response budget or size guard can cut the part. The answer is `{complete, totalLines, versionToken, hash, fenceCleared, persisted, implicitOperations}` plus the identity that was read; the content is not part of it.
  - The evidence is the Worker's certificate, never an argument: a client cannot declare a read complete. The fence is cleared only when the object, part, type, guid and entity key it recorded match what the Worker read, the version token and hash describe the same bytes, nothing wrote the object while it was read, and a second read right before clearing is identical; a fence re-armed meanwhile, a `baseVersion` that moved, or an unusable journal leave it in place. Fences of other objects, parts, types or guids, KB-level fences and property fences are never cleared by it.
  - `dryRun` defaults to `true` and only inspects (it still re-reads and reports `wouldClear`); `dryRun=false` rewrites the recovery journal and nothing else. It performs no Specify, Generate, Build, Rebuild, reorganization, execution or test and writes no object. When no fence matches, the answer lists same-object fences recorded under another KB alias, part or identity instead of reporting nothing, and the `PostTimeoutReadRequired` error now carries this call as a next step.
  - Clearing a fence never says the write that timed out landed, so the answer also carries `timedOutWrite`: `notApplied` when the part is still at the `baseVersion` that write was made against, `changed` when it moved, `unknown` when the write carried no `baseVersion`. `persisted` only says the journal change is durable. The next step in the `PostTimeoutReadRequired` error inspects first (`dryRun=true`). A fence already cleared by another route while the call ran answers `already-cleared`, not an error.

- The protected SDK CI lane now compiles the Release Worker live-test assembly against the selected SDK before packaging and no-build live execution. Clean runners no longer depend on stale local test outputs; compilation failures block validation.

- Lifecycle index jobs now wait for the same Worker operation to finish with a current, ready index. Background acknowledgements, cancellation and observer timeouts no longer imply successful completion.
